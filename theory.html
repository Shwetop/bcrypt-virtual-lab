Hashing vs. Encryption

Two fundamentally different cryptographic operations

A common misconception in security is confusing hashing with encryption. Both use mathematical functions, but their goals and reversibility are entirely different.

Encryption

✓ Reversible (Two-Way)
Purpose Secure confidential data during transmission or storage
Reversible? Yes — decryption restores original plaintext via key
Key Needed Symmetric (AES, DES) or Asymmetric (RSA)
Output Size Variable — proportional to input length
Examples AES-256, RSA, TLS, PGP, BitLocker
Use Cases HTTPS, file encryption, secure messaging, VPNs

Cryptographic Hashing

✗ Irreversible (One-Way)
Purpose Data integrity verification and safe authentication
Reversible? No — mathematically infeasible to recover input
Key Needed None — deterministic from input alone
Output Size Fixed length regardless of input size
Examples MD5, SHA-256, Bcrypt, Argon2, PBKDF2
Use Cases Password storage, file checksums, digital signatures
Key Takeaway: You should never encrypt passwords — you should hash them. Encrypted passwords can be decrypted if the key is stolen. Hashed passwords cannot be reversed, making them safe to store even if the database is breached.

Why Bcrypt?

The problem with fast hashing algorithms for passwords

Hash functions like MD5, SHA-1, and SHA-256 were designed for throughput — verifying file integrity over gigabytes of data. This speed is a critical vulnerability when used for password storage.

100B+/sec SHA-256 hashes/sec
on modern GPU
130K+/sec MD5 hashes/sec
per GPU cluster
~10/sec Bcrypt (cost 10)
deliberately slow
The GPU Brute-Force Threat:

With 100 billion SHA-256 hashes per second, an attacker can brute-force every possible 8-character password combination (letters + digits + symbols = ~6.7 trillion combos) in under 70 seconds. Bcrypt at cost 10 would take over 21 years for the same attack.

Enter Bcrypt: Intentionally Slow by Design

Created in 1999 by Niels Provos and David Mazières at OpenBSD, based on the Blowfish cipher, Bcrypt introduces:

Key Stretching
Thousands of expensive Blowfish rounds that burn CPU cycles intentionally
Adaptive Cost Factor
As hardware gets faster, simply increase the cost to keep up — no algorithm change needed

Salt & Work Factor

Random entropy injection and exponential cost scaling

1. What is a Cryptographic Salt?

A Salt is a unique 128-bit (16-byte) random value generated for every password hash. Bcrypt automatically generates and embeds the salt into the output hash string, so you never need to store it separately.

Defeats Rainbow Tables

Precomputed hash lookup tables are useless — the unique salt means attackers must recompute a custom table for each individual user, requiring 2128 separate tables.

Prevents Hash Correlation

Two users with identical passwords (e.g. "Password123") will have completely different Bcrypt hashes — an attacker cannot spot duplicate passwords in the database.

2. The 2Cost Factor Exponential Work Formula

Bcrypt's internal Blowfish key expansion rounds scale exponentially with the cost parameter:

Iterations  =  2 Cost Factor

⬆ Increasing cost by 1 doubles the computation time

Cost Factor Formula Iterations Approx. Time (modern CPU) Recommended Use
4 24 16 ~1 ms Testing only
8 28 256 ~10 ms Low-power devices
10 210 1,024 ~100 ms ✓ Recommended

The 72-Byte Password Limitation

A critical architectural constraint in the Eksblowfish cipher

Bcrypt is built on Eksblowfish (Expensive Key Schedule Blowfish), which enforces a hard maximum key input of 72 bytes. Any password bytes beyond position 72 are silently dropped.

Silent Truncation Example
Password A: "A" × 72 bytes + "SecretSuffix1"
Password B: "A" × 72 bytes + "TotallyDifferent"
Both produce the EXACT SAME Bcrypt hash — the red parts are silently discarded
Security Impact: If two users have the same first 72 bytes of password but different suffixes, their accounts become interchangeably accessible — either password will log in to both accounts.

Industry Workaround: SHA-256 Pre-Hashing

Modern frameworks (e.g. Django, Laravel) pre-hash the password with SHA-256 first, so input to Bcrypt is always a fixed 44-character Base64 string — well under 72 bytes:

Plaintext Password Any length
SHA-256 Hash 32 bytes / 256 bits
Base64 Encode 44 ASCII chars
Bcrypt Hash 44 chars < 72 bytes ✅
Result: SHA-256 output is always exactly 256 bits = 32 bytes. Base64 encoding gives exactly 44 ASCII characters — safely under the 72-byte limit, with full preservation of long-password uniqueness.
