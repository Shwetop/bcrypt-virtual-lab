Cryptographic Theory & Concepts

Hashing vs. Encryption: Fundamental Distinction

A common misconception in security is confusing hashing with encryption. Both use mathematical functions, but their design goals and reversibility differ fundamentally.

Encryption (Two-Way)

  • Purpose: Confidentiality during data transmission or storage.
  • Reversibility: Reversible. Ciphertext can be decrypted back to plaintext using a secret key.
  • Key Requirement: Uses symmetric (AES, DES) or asymmetric (RSA) keys.
  • Output Length: Proportional to input payload size.
  • Use Case: SSL/TLS web traffic, encrypted disk storage, secure messaging.

Cryptographic Hashing (One-Way)

  • Purpose: Data integrity verification and safe authentication.
  • Reversibility: Irreversible. It is mathematically infeasible to derive plaintext from a hash.
  • Key Requirement: Does not require a secret decryption key.
  • Output Length: Fixed length regardless of input size (e.g. Bcrypt is 60 chars).
  • Use Case: User password storage, file checksums, digital signatures.

Why MD5 and SHA-256 Fail for Passwords

Traditional cryptographic hash functions like MD5, SHA-1, and SHA-256 were designed for high throughput (hashing gigabytes of data per second). While ideal for integrity checks, high speed is a fatal flaw for password storage!

The GPU & ASIC Threat: Modern consumer GPUs can compute over 100 billion SHA-256 hashes per second. An attacker with a leaked password database can brute-force 8-character complex passwords in minutes using rainbow tables and parallel cracking tools like Hashcat.

Enter Bcrypt: The Slow Hash Algorithm

Created by Niels Provos and David Mazières in 1999 based on the Blowfish cipher, Bcrypt introduces Key Stretching and an adaptive cost factor. It forces the CPU/GPU to perform thousands of rounds of expensive memory-hard operations for every single password attempt, making brute-force attacks computationally infeasible.

Cryptographic Salt & The Exponential Work Factor

1. The Role of Cryptographic Salt

A Salt is a unique, randomly generated 128-bit (16-byte) string appended to the password before hashing. Bcrypt automatically embeds this salt into the final hash output.

Defeats Rainbow Tables: Rainbow tables are giant precomputed lookup tables of plaintext-to-hash pairs. Adding a unique 128-bit salt means attackers must compute a custom rainbow table for every single user salt (2128 variations).
Prevents Hash Correlation: If two users have the exact same password (e.g., "Password123"), different random salts ensure their resulting Bcrypt hashes look completely unique in the database.

2. The 2Cost Factor Exponential Work Formula

Bcrypt's work factor is controlled by an integer parameter Cost Factor (C). The total number of internal Blowfish key expansion iterations is calculated as:

Total Key Expansion Iterations = 2Cost Factor

Because it is an exponential formula, increasing the cost factor by 1 doubles the CPU computation time required to hash a password.

  • Cost 8: 28 = 256 iterations
  • Cost 10: 210 = 1,024 iterations (standard baseline)
  • Cost 12: 212 = 4,096 iterations (high security)
  • Cost 14: 214 = 16,384 iterations (heavy delay)

The 72-Byte Password Limitation

A critical architectural detail of Bcrypt is that it is built on top of Eksblowfish (Expensive Key Schedule Blowfish), which enforces a strict maximum password key length of 72 bytes (72 ASCII characters).

The Silent Truncation Vulnerability: Any password longer than 72 bytes is silently truncated by standard Bcrypt implementations! For example, "A" * 72 + "SuperSecretSuffix1" and "A" * 72 + "DifferentSuffix2" will produce the EXACT same hash.

Industry Standard Workaround: Pre-Hashing with SHA-256

To safely allow passwords of arbitrary length (e.g. 100+ character passphrases) without silent truncation, modern security frameworks pre-hash the raw password using SHA-256 before passing it to Bcrypt:

Bcrypt Input = Base64( SHA-256( Plaintext Password ) )   (Fixed 44 ASCII chars < 72 bytes)
